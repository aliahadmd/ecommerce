## Why this matters

Seller money — real payout exposure — relies on check-then-act patterns with
no database backstop:

1. **Double `sale` ledger entries.** `ledgerSaleForSubOrder` is
   "idempotent" via a SELECT-then-INSERT, and `seller_ledger` has only a
   plain index (`seller_ledger_shop_idx`) — no unique constraint on
   `(sub_order_id, kind)`. The caller (`updateSubOrderStatus`) reads the
   sub-order's status OUTSIDE its transaction, so two concurrent
   "Mark delivered" requests both pass `canTransition`, both SELECT (find no
   sale row), both INSERT → the seller's `earned` total and payout-available
   balance double-count one order.
2. **Over-spent payouts.** `createPayout` sums `net_cents`, compares to the
   requested amount, then inserts the payout + a negative ledger row — all
   without locking any row for the shop. Two concurrent payouts both see the
   pre-payout balance and both succeed → up to 2x the available balance paid
   out, negative ledger balance after the fact.

Both fixes are cheap and additive; both should exist before real money moves.

## Steps

### Step 1: Unique index on the ledger

In `packages/db/src/schema/settings.ts`, extend the `sellerLedger` table
config array:

```ts
(t) => [
  index("seller_ledger_shop_idx").on(t.shopId, t.createdAt),
  uniqueIndex("seller_ledger_sub_kind_uq").on(t.subOrderId, t.kind),
]
```

Import `uniqueIndex` from `drizzle-orm/pg-core` (via whatever import list
the file already uses — match it). Postgres unique indexes treat NULLs as
distinct, so the NULL-`sub_order_id` payout rows never conflict — no partial
index needed.

**Verify**: `pnpm typecheck` → exit 0.

### Step 2: Generate + apply the migration

Run `pnpm db:generate` (with the dev DB NOT required for generation). Inspect
the generated `packages/db/drizzle/0021_*.sql`: it must contain exactly one
`CREATE UNIQUE INDEX "seller_ledger_sub_kind_uq" ON "seller_ledger" ...`.
If drizzle wants to emit anything else (e.g. it noticed unrelated drift),
STOP and report. Apply with `pnpm db:migrate` (docker compose postgres must
be up).

**Verify**: `pnpm db:migrate` → exit 0; and
`docker compose exec postgres psql -U postgres -d ecommerce -c "\di seller_ledger_sub_kind_uq"`
→ the index exists (adjust container/user/db names to match
`docker-compose.yml` if different — check it).

### Step 3: Guard the delivered transition

In `apps/web/src/server/sub-orders.ts`, make the forward transition update
conditional so a concurrent transition loses instead of double-applying:

```ts
await db.transaction(async (tx) => {
  const updated = await tx
    .update(schema.subOrders)
    .set({ status: data.status })
    .where(
      and(
        eq(schema.subOrders.id, data.subOrderId),
        eq(schema.subOrders.status, row.sub.status) // only from the state we verified
      )
    )
    .returning({ id: schema.subOrders.id })
  if (updated.length === 0) {
    throw new AppError("INVALID", "This sub-order was already updated")
  }
  await recomputeOrderStatus(tx, row.sub.orderId)
  if (data.status === "delivered") {
    const { ledgerSaleForSubOrder } = await import("./payouts-internals")
    await ledgerSaleForSubOrder(tx, data.subOrderId)
  }
})
```

Keep the surrounding code (role checks, `canTransition`, the cancel branch)
exactly as-is. With step 1's unique index, even a lost race can no longer
double-insert the sale row (the second tx aborts on the constraint).

**Verify**: `pnpm typecheck` → exit 0.

### Step 4: Serialize payout creation on the shop row

In `apps/web/src/server/payouts.ts`, at the TOP of the `createPayout`
transaction (before the sum), lock the shop row so concurrent payouts for
the same shop serialize:

```ts
await db.transaction(async (tx) => {
  await tx
    .select({ id: schema.shops.id })
    .from(schema.shops)
    .where(eq(schema.shops.id, data.shopId))
    .for("update")
  // ...existing balance read + inserts unchanged
})
```

**Verify**: `pnpm typecheck` → exit 0.
