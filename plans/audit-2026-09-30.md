## 3. New findings — High

### H1. Seller ledger subtracts the coupon discount twice → sellers underpaid
- **Where:** `apps/web/src/server/payouts-internals.ts:43` — `gross = sub.totalCents - sub.discountCents`
- **Why:** `sub_orders.total_cents` is already `subtotal + shipping − discount` (`commerce.ts:594`).
- **Evidence:** $100 sub-order, $10 coupon → ledger gross **$80**, should be **$90**. Every coupon order under-credits the seller by the discount share; commission is also computed on the wrong base.
- **Fix:** `gross = sub.totalCents`. Add a reconciliation test (ledger gross sum == sub-order totals).

### H2. Admin "commission rate" setting has no effect
- **Where:** admin saves into key `store.settings` (`settings.ts:8`, field `commissionRate`); the ledger reads key `commerce.commission_rate` (`payouts-internals.ts:12`, `payouts.ts:18`). Nothing ever writes `commerce.commission_rate`.
- **Impact:** commission is always the hardcoded 10% regardless of what the admin configures. The settings page silently lies.
- **Fix:** have `getCommissionPercent` read `store.settings.commissionRate` (single source); delete the duplicate in `payouts.ts`.

### H3. Parent order status is stuck at `pending` for every in-progress order
- **Where:** `apps/web/src/server/internals.ts:92-94` (`recomputeOrderStatus`)
- **Why:** `derived` starts at `"pending"` (rank 0) and is only replaced by a *lower* rank — impossible. Only "all delivered" and "all cancelled" derive correctly.
- **Evidence (executed):** `["shipped"] → pending`, `["confirmed","confirmed"] → pending`, `["shipped","delivered"] → pending`.
- **Impact:** buyers see "pending" on shipped orders (`account/orders/index.tsx:53`, `$id.tsx:46`), the buyer cancel banner keys off it (`$id.tsx:55`), admin order list and admin/seller dashboard counts (`admin.ts` pendingOrders uses `orders.status in (pending, confirmed)`) are wrong.
- **Fix:** start from the highest rank (`delivered`) and take the minimum, or `min(rank)` over active sub-orders. Extract as a pure function and unit-test it (plan-3 §4 said it would be).

### H4. Shop-scoped coupons discount the entire multi-shop cart and bill other sellers
- **Where:** `coupons-internals.ts:28-40` (`computeDiscountCents` on full subtotal), `commerce.ts:391-404` (subtotal of all items), allocation `commerce.ts:580-583` (proportional across **all** sub-orders).
- **Impact:** a coupon scoped to Shop A applied to a cart with Shops A+B discounts B's items and B's sub-order/ledger absorbs part of A's promotion.
- **Fix:** for `shopId` coupons, compute on that shop's subtotal and allocate only to that shop's sub-order.

### H5. Unpaid card orders can be fulfilled, credited to the seller, and hold stock forever
- **Where:** `sub-orders.ts:235-262` — forward transitions check only role/ownership + `canTransition`; no payment check. Delivery then writes a `sale` ledger row (`sub-orders.ts:260-262`).
- **Impact:** a seller can ship a card order whose payment is `requires_payment`/`failed`; on delivery the seller is credited revenue that was never collected and can be paid out. Abandoned card checkouts keep their stock decremented indefinitely (no expiry / auto-cancel job).
- **Fix:** block `confirmed`+ transitions for `method=card` unless payment `succeeded`; add a BullMQ repeatable job that cancels unpaid card orders after N minutes (restoring stock).

### H6. Production worker cannot run → no email in production
Three independent defects:
1. `Dockerfile.worker:19-22` copies `node_modules`, `packages`, `apps/worker` from the `deps` stage, which only ran `pnpm fetch` on `package.json` files — no installed modules, no source code.
2. `docker-compose.prod.example.yml` worker env sets `NODE_ENV=production` but omits `S3_*`, `BETTER_AUTH_*`, `SMTP_USER/PASS`, `EMAIL_FROM` → `assertProductionEnv()` (`packages/config/src/env.ts:85`) throws at boot.
3. Worker healthcheck (`docker-compose.prod.example.yml:47`) probes `127.0.0.1:3000/api/health` inside the worker container, where nothing listens → permanently unhealthy.
- Also: README deploy section omits the worker entirely (README #10).

### H7. Seed has no production guard and ships known credentials
- **Where:** `scripts/seed.ts:47-48` creates `seller@dev.local / Seller1234!` and `buyer@dev.local / Buyer1234!` (verified, active shop, demo products, coupon `E2E10`); `SUPER_ADMIN_PASSWORD` defaults to `Admin1234!` (`env.ts:43`) and is **not** in `PROD_REQUIRED` / `PROD_FORBIDDEN_DEFAULTS` (`env.ts:66-83`).
- **Impact:** the seed is the only documented way to create the first super admin, so running it in production creates publicly-documented login credentials (README table lists them).
- **Fix:** refuse to run when `NODE_ENV=production` unless `--admin-only`; add `SUPER_ADMIN_PASSWORD` to the prod-forbidden defaults; split admin bootstrap from demo data.
